# 收运证据审计与承运商 SLA 绩效服务

面向物业经理、数据团队与财务的可审计平台，包含两个相互独立又共享证据口径的领域：

1. **计量域（收运批次重量一致性与计费差异）**：对同一收运批次，环卫（门岗/任务）、地磅与处理场给出不同的重量、时间与费用依据，本服务把三方证据汇总为可审计的收运重量、计费依据与差异范围。
2. **绩效域（承运商服务水平 SLA 月度评分）**：把排班承诺、车辆到场、处理场签收、居民投诉与主管裁定关联到真正受影响的收运任务，判断承运商是否达到合同服务水平。

**服务边界**：不派车、不预约卸料、不审批付款；只发布可审计的数据产品与评分/调整记录。

---

## 一、SLA 绩效域（本题核心）

### 关键业务规则

- **评分资格**：只有**已确认合同**窗口内、且有合同条款及证据支持的服务任务才进入评分；未确认合同的任务标记 `excluded` 并列风险，不参与扣分。
- **不靠投诉数量扣分**：未核实投诉**只列风险、不直接扣分**；核实并关联到具体受影响车次后才计罚。只看完成率也无法掩盖重复登记与迟到补录——漏收、到场超时、迟到签收分别由排班/到场/签收证据独立判定。
- **重复投诉合并去重**：按**地址（文本或经纬度距离）、事件时间窗与事件关系**形成合并候选；主管确认同一事件后整组**只计一次罚分**，多人报告同一问题不重复计罚；解除合并后才按独立投诉分别计。
- **申辩与裁定并列保存**：承运商申辩与主管裁定逐条对应、并列留痕；申辩只改变对应任务的裁定状态（`overturned` 撤销违约 / `upheld` 维持）。
- **两种月度评分模式**（同一合同窗口与同一套任务证据，口径一致）：

  | 模式 | 反馈速度 | 稳定性 | 行为 |
  | --- | --- | --- | --- |
  | 增量更新 `incremental` | 证据到达即可重算，较早反映纠正结果 | 同月分数会多次变化 | 每个版本记录**受影响车次**，可逐版本追溯；无变化不制造空版本 |
  | 月结统一 `month_end` | 月内只展示进度与证据缺口 | 月结证据批次锁定后统一计算，稳定可复核 | 锁定后迟到签收等另出**调整单** |

- **月结锁定与调整单**：锁定后评分不可改写；迟到签收、付款后核实的投诉、付款后的追溯裁定一律形成**调整单**，旧付款凭证不改写。已支付罚款被申辩推翻时，以**负差额**调整记录返还。
- **并发处理**：申辩结论与评分发布并发时，评分置 `review_required`，主管需重新查看影响车次并重算后才能再发布；月结锁定（或已付款）后的裁定不走重算，直接落调整单。
- **评分下钻**：经理可从评分逐车次下钻到**合同条款、任务证据（到场/签收/投诉，含内容哈希）与裁决记录**。

### 罚则与判定（种子合同 HT-2026-SLA-1，可在合同确认时配置）

| 违约类型 | 判定依据 | 罚分 |
| --- | --- | --- |
| 漏收 `missed_collection` | 承诺排班无任何车辆到场证据 | 8 |
| 到场超时 `late_arrival` | 到场晚于承诺 + 容差（10 分钟） | 3 |
| 迟到签收 `late_receipt` | 处理场签收晚于承诺 + 时限（24 小时） | 2 |
| 核实投诉 `valid_complaint` | 已核实并关联本任务的投诉（合并去重后） | 5 |

### SLA 演示数据（2026-11 服务月，`backend/seed_sla.py`，幂等）

10 个合格车次 + 1 个被排除车次，覆盖：

- 全程合规、漏收、到场超时、迟到签收四类判定；
- 梧桐里 12 号两位居民 50 分钟内重复投诉 → 合并候选 → 确认同一事件只计一次；
- 海棠巷超时申辩被**采纳**（撤销违约）、城东小区漏收申辩被**驳回**（维持）；
- 增量评分 3 个版本：v1=87（4 车次）→ v2=74（受影响 2 车次）→ v3=69（受影响仅 T8）；
- 月结统一计算 69 分 → 锁定 → 登记付款；
- 付款后三笔调整单：迟到签收 **+2**、投诉核实 **+5**、漏收申辩采纳返还 **−8**，净 −1，**调整后 70 分**，原锁定分与付款凭证保持 69 不变；
- 未核投诉、孤儿投诉、签收证据缺口、被排除任务均只出现在风险/缺口列表。

### SLA 界面入口

- **服务绩效评分**（`/performance`）：切换增量/月结模式，查看分数卡片、版本流水与受影响车次、任务级明细、风险缺口、月结调整单；按角色显示运行/发布/锁定/付款/调整操作。
- **投诉与裁定**（`/sla`）：数据团队录入排班/到场/签收/投诉证据与承运商申辩；主管扫描合并候选、确认/解除合并、核实/驳回投诉、对申辩做裁定。
- **车次下钻**（`/sla/tasks/:id`）：合同条款 → 合规判定 → 到场/签收/投诉证据（哈希）→ 申辩与主管裁决。

## 二、计量域（保留并完整可用）

| 组件 | 职责 |
| --- | --- |
| 来源证据库 | 保存任务、门岗、地磅、签收、费率目录、账务回执的原文、事件时间、设备/场地标识、校准版本与 SHA-256 内容哈希 |
| 批次关系册 | 维护任务/车辆/称重/签收的候选/确认关联；同一称重被两批次候选引用时冻结分配 |
| 计量裁定器 | 按合同策略签发合同计费重量（优先级）或可接受区间（区间），记录待核冲突与排除原因 |
| 费率编译器 | 仅在冻结目录上生成金额事实；目录服务后修订产生新解释版本，不回写历史 |
| 差异发布器 | 输出计费依据、未决范围与下游引用版本（`PUB-{批次}-vN`），发布不可变 |

计量域六个验收场景（2026-10 服务月，7 个批次）与既有行为保持不变，详见下文「验证方式」。

## 技术栈与结构

React 18 + Vite ｜ FastAPI + SQLAlchemy 2 ｜ PostgreSQL（JSONB 存证据负载与评分/裁定明细）

```
backend/
  app/
    models.py            # 计量域模型 + SLA 模型（排班/到场/签收/投诉/合并组/申辩/裁定/评分/版本/调整单）
    db.py                # 建表 + 轻量列迁移（旧库只补列不重建）
    services/
      # 计量域
      evidence · registry · adjudicator · compiler · publisher · departure · calibration
      # SLA 绩效域
      sla_evidence.py    # 排班/到场/签收/投诉录入（内容哈希、到场自动匹配车次）
      sla_complaints.py  # 合并候选（地址+时间窗+地理半径）、核实/驳回
      sla_adherence.py   # 逐车次合规判定（四类违约、合并去重、申辩撤销、风险）
      sla_appeals.py     # 承运商申辩与主管裁定（并发标记/调整单）
      sla_scoring.py     # 双模式评分、版本流水、发布/锁定/付款、调整单、月内进度
    api/
      auth · evidence · batches · catalogs · reports
      performance.py     # SLA 全部 /api/sla/* 端点（26 条路由）
    main.py              # 生产模式同时托管 frontend/dist，未知 /api 返回 404
  seed.py                # 计量域六个验收场景（幂等）
  seed_sla.py            # SLA 绩效域演示数据（幂等）
  tests/                 # test_acceptance.py（12）+ test_sla_scoring.py（17）
frontend/                # React SPA：计量域 6 页 + 绩效域 3 页（服务绩效/投诉裁定/车次下钻）
docker-compose.yml       # db + backend + frontend 一键启动
```

## 快速开始

### 方式一：Docker Compose（一键）

```bash
docker compose up --build
```

- 前端：http://localhost:8080 （nginx 反向代理 `/api` 到后端）
- 后端 API：http://localhost:8000/api （容器内自动建表并写入计量域 + SLA 演示数据）

> 注：本交付容器内无 docker 命令，Compose 配置已通过 YAML 结构校验，未在本容器实际 `compose up`；本地开发验证见下文。

### 方式二：本地开发

前置：PostgreSQL 运行于 127.0.0.1:5432（库/用户/密码均为 `ccdev`，可用 `DATABASE_URL` 覆盖）。

```bash
# 后端（终端 1）
cd backend
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python seed.py                 # 建表 + 写入计量域与 SLA 演示数据（幂等，可重复执行）
.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000

# 前端（终端 2，开发模式，/api 代理到 8000）
cd frontend
npm install
npm run dev                              # http://localhost:5173
```

单端口验证（后端托管前端构建产物）：

```bash
cd frontend && npm run build && cd ../backend
.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000   # http://127.0.0.1:8000
```

## API 概览

计量域接口位于 `/api`（证据、批次、合同/目录、校准、复核队列、月结报表、发布记录），SLA 绩效域统一位于 `/api/sla`，除登录外均需 `Authorization: Bearer <token>`：

- `POST /api/sla/contracts/{id}/confirm` — 主管确认合同并写入 SLA 条款
- `GET/POST /api/sla/tasks` · `GET /api/sla/tasks/{id}` — 排班承诺与车次下钻（条款+证据+裁决）
- `GET/POST /api/sla/arrivals` · `GET/POST /api/sla/signoffs` — 车辆到场（自动匹配车次）/ 处理场签收（锁定后自动转调整单）
- `GET/POST /api/sla/complaints` · `POST /api/sla/complaints/detect-merges` · `POST /api/sla/complaints/{id}/verify`
- `GET /api/sla/merge-groups` · `POST /api/sla/merge-groups/{id}/decision`
- `GET/POST /api/sla/appeals` · `POST /api/sla/appeals/{id}/rule` — 申辩与主管裁定
- `POST /api/sla/scoring/run|publish|lock|mark-paid` · `GET /api/sla/scoring` · `GET /api/sla/scoring/list`
- `GET /api/sla/progress` — 月结模式月内进度与证据缺口
- `GET /api/sla/adjustments` · `POST /api/sla/adjustments/{id}/apply` — 月结调整单

所有评分、版本、裁定与调整均为追加/版本化记录，历史与已支付凭证不回写。
